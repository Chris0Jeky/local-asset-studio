## Decision: explicit replacement, not permissive switching

On a continued picture-based Combine pair, **Replace pose picture with drawing** renders the current drawing, replaces only the first pose slot, and selects `combine-klein-9b-skeleton`. The character, continuation identity, seed, dimensions, batch count and named answers stay attached. The old donor is not deleted from the library. Its parent claim is removed only when it is not also the kept character.

On the skeleton recipe the action remains **Use this pose**. Ordinary engine buttons still refuse picture/skeleton reinterpretation. Extra reference pictures, missing character attachment, pending file selection and unavailable target runtime still block replacement. An empty or missing first pose slot does not block the repair because that is precisely the input being replaced.

Who/pose/clothes answers transfer by meaning and are projected into the target recipe's image order. Old manually edited prompt text for a different source pair is not restored. The existing pair's manual wording is retained in the engine-switch cache. The new drawing may intentionally disagree with the retained pose wording; the action tells the user to review it before Generate, rather than inventing an automatic description or claiming semantic consistency.

## Response and state checks

The action captures the exact serialized drawing and workbench state before rendering. While unresolved, Generate, engine buttons and geometry mutation controls are held. A changed workbench or drawing invalidates the reply. The response must name the expected guide filename format, dimensions, renderer, bounded byte count, SHA-256 identities and `generation_submitted: false` before any attachment or recipe switch.

Only the supported response fields are projected: a returned role, missing flag or parent-asset claim cannot overwrite the target slot's ownership. This is response-envelope validation, not cryptographic authentication, source-image inspection, pixel verification or a Workspace transaction. The server and its existing tests still own actual PNG storage and graph binding.

A render failure, malformed response or stale state keeps the current recipe and source pair. No automatic retry is made. A guide already written by the server can remain an unused upload after a rejected late response, exactly as with other upload paths; there is no automatic deletion or hidden reattachment. Persistence and uncertain-upload journaling are not implemented by this client-only handoff change.
