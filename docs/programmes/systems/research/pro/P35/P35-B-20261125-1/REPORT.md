## Existing-route contracts and principal disconfirming tests

### Klein 4B reference baseline

Official architecture: FLUX.2 Klein 4B is a rectified-flow transformer; distilled models target four steps and combine text-to-image and multi-reference editing. BFL's published interface supports up to four references. The current Studio graph uses an FP8 4B backbone, Qwen3 4B text encoder, FLUX.2 VAE, six Euler steps, Flux2 schedule, CFG 1 and a 1024×1536 output. Each reference is independently resized to approximately one megapixel, VAE-encoded, then appended in order. The supported model count must not be inferred from an arbitrarily long chain of generic reference nodes. [S01–S04]

`combine-klein`: source/character is image 1 (node 14), pose board begins at image 2 (node 20), optional third image is node 24. Its current positive-conditioning chain is `CLIPTextEncode → ReferenceLatent → ReferenceLatent → ReferenceLatent → CFGGuider`. `Flux2Scheduler.width/height` and `EmptyFlux2LatentImage.width/height` must stay synchronized. `ReferenceLatent(conditioning, latent)` appends `latent.samples` under `reference_latents`; it supplies no identity/pose/style enforcement by itself. [S05; local graph]

Disconfirm usefulness if it repeatedly preserves identity only by losing the requested pose, or borrows clothes/palette/background from the pose reference. A quick successful standing pose does not establish foreshortening, contact, floor or two-actor performance.

### Klein 9B Copy Pose and skeleton incumbent pair

Both current routes use distilled `flux-2-klein-9b-Q6_K.gguf`, Qwen3 8B mixed FP8 text encoder and FLUX.2 VAE, through `UnetLoaderGGUF`, six Euler/Flux2 steps and CFG 1. Official 9B is also rectified flow, with a separate 8B Qwen3 encoder; GGUF is an Unsloth conversion using city96 tooling. [S06–S08]

Copy Pose adds `KleinBase9B_PoseTransfer.safetensors` through `LoraLoaderModelOnly`, strength 1.0. Image 1 is the character, image 2 the pose. Preserve the exact authored trigger and specify character, costume colours, hands and camera. Its model name and recorded creator metadata identify a **9B-base-trained adapter applied here to a distilled 9B backbone**. Historical output exists, but that does not erase the compatibility/quality question.

Skeleton has **reversed roles**: image 1 is a coloured stick figure on black, image 2 the character. It uses ordinary FLUX reference latents, not an OpenPose ControlNet. The drawing is a visual instruction that the model may follow or reproduce. The Studio's renderer identity, joint convention, line width, canvas and bytes belong in every receipt. These two routes cannot share positional reference bindings blindly. [local catalog and graphs]

Primary disconfirmation: Copy Pose leaks the pose actor or outfit; skeleton loses depth/contact or paints guide marks; both omit design details under extreme views. Test original/unfamiliar characters without a known character name, because the local SDXL probe already found a familiar-name tag doing work attributed to its adapter. Include one deliberate wrong-limb guide to establish whether geometry is actually followed, separately from whether it is artistically good. Do not promote because a metric rewards obedience to a wrong pose.

The separate depth route is useful background research, not needed in this four-graph slice. Its currently recorded `DepthAnythingV2Preprocessor` uses **vitl / Large**, whose weights are CC-BY-NC-4.0; only Small is Apache-2.0. A public Apache code repository does not establish that every depth model has the same terms. Depth maps can carry clothing/body volume and footwear shape that a skeleton does not. [S09; local catalog]

### Qwen-Image-Edit-2511 three-reference challenger

The 20B Qwen image family uses MMDiT and a Qwen2.5-VL 7B visual-language encoder plus Qwen VAE. September's 2509 release introduced multi-image editing and says 1–3 images work best; 2511 claims improved character and multi-person consistency. These are general publisher claims, not an anime/contact qualification. The 2511 official example uses 40 steps and true CFG 4, so it does not establish the quality of the Studio's four-step Lightning graph. [S10–S12]

Current graph: Q4_K_M backbone; `qwen_2.5_vl_7b_fp8_scaled`; `qwen_image_vae`; exact `Qwen-Image-Edit-2511-Lightning-4steps-V1.0-bf16` at 1.0; AuraFlow shift 3.1; Euler/simple, four steps, CFG 1; 832×1248 empty SD3 latent; tiled VAE decode (tile 256, overlap 64). Identity/pose/style are image1/image2/image3 in **both** positive and negative `TextEncodeQwenImageEditPlus` nodes, then `FluxKontextMultiReferenceLatentMethod=index_timestep_zero`. [local graph; S13]

Current upstream `TextEncodeQwenImageEditPlus` accepts `clip`, `prompt`, optional `vae`, `image1..image3`; yields conditioning. The language branch resizes each picture to about 384² pixels, while the VAE branch uses about 1024² on an eight-pixel grid. Thus the two branches do not see identical detail. Keep explicit `Picture 1/2/3` role wording. Native acceptance of depth/keypoint images means visual conditioning; it does not mean that an SDXL ControlNet is interchangeable with Qwen. [S14]

Disconfirm this candidate before a quality campaign if one authorized smoke run exceeds the declared memory/time envelope, crashes, loses output history, or requires uncontrolled environment changes. If viable, compare the current Lightning route by its own results; do not label the base model disproved by a four-step adapter failure.

Official release September 20, 2026: 7B visual generator, 32 single-stream DiT blocks, mixed-granularity attention and prefix KV cache reuse; Qwen3-VL 8B encoder; its own 64-channel latent / RGBA-capable VAE. Upstream `TextEncodeQwenImage21` currently exposes `clip`, `prompt`, `negative_prompt`, optional `vae`, `resolution`, and `images.image_1` through `images.image_16`; outputs positive, negative and a first-reference-sized latent. The node accepts 16 slots; the model card promises ten. Use ten as the source-backed maximum, and two/three for first local qualification. It rescales each reference to a 32-pixel grid and processes the first image of each input batch. Alpha is composited over white for vision while the VAE retains alpha. The experimental cache node exposes devices auto/GPU/CPU/off and default/int8/int4 storage; this is another quality/resource condition to pin. [S14, S18]

The Comfy distribution lists 6.76 GB image weights, 8.71 GB int8 encoder and 644.2 MB VAE. Their sum is not peak memory. ### FLUX 3 Image Klein

Official release October 15, 2026: 5.6B image transformer, Qwen3-VL-4B-Instruct encoder, FLUX.2 packed autoencoder; distilled 16-step no-guidance checkpoint, up to ten references. The separate prompt upsampler is a 9B model. BFL permits replacing it with another LLM/full scene caption using its supplied system prompt; store the resulting caption and reference mapping. A terse edit instruction cannot be assumed equivalent. [S20–S22]

The reference node appends latents to both conditioning branches and returns the output latent. **The template's Markdown note still says 50 steps/CFG 3.5; its actual distilled widgets say 16/1.** Use machine graph settings and pin the resolved template. [S23]

BFL's layout language uses boxes on a 0–1000 grid in top/left/bottom/right order. Boxes specify intended position/scale; they are not masks. The official card explicitly allows spill beyond boxes and changes outside an edit region. Its API's pixel restoration feature is not evidence of exact local pixel preservation. Maintain protected-region compositing/validation independently. [S20, S24]

The official Comfy package reports approximately 5.8 GB transformer, 4.9 GB encoder, 0.3 GB VAE and 6.7 GB w4a8 (or 9.8 GB int8) prompt upsampler. This is storage footprint, not simultaneous residency. BFL's 8 GB consumer claim is for NVIDIA INT8 Comfy; its reference code reports 31/26/25 GB BF16/FP8/NVFP4 peak without upsampler on B200, and has no INT8 path. None establishes Windows AMD kernel availability or peak memory. NVFP4 is a Blackwell path and is not the RX9070XT candidate. [S21, S22, S25]

FLUX.2 9B KV is a legitimate official model but is a lower priority here: a speed-oriented caching variant does not directly establish better identity/contact results, and the official full-precision footprint is approximately 29 GB. Record dedicated/shared GPU, PyTorch allocated/reserved, process working set/private commit, system commit limit/headroom and available physical RAM at load, reference encoding, sampling and VAE decode; capture cold/warm separately. File storage size is neither GPU residency nor host commit. Pagefile capacity is not usable physical RAM or proof of responsiveness. More references increase token/activation/cache cost even when weights are unchanged.

Proposed bounded rules (plan, not implemented controls): begin with one smoke case per high-risk route; run one job at a time; require known empty queues and no unresolved attempt; respect existing GPU lease/admission; stop the route on the first OOM, host allocation failure, native access violation, backend loss, unbounded memory growth, missing telemetry or budget overrun. A stall ends submissions and requires reconciliation; it does not authorize killing an unknown process. Preserve submission receipt/prompt ID and never auto-retry an uncertain job. Stop the quality campaign if resources cannot be measured reliably. No model or runtime update is a permissible hidden retry.

## Acceptance and falsifiability

Use independent identity, costume, style, geometry, contact/anatomy and scene judgements. The owner’s **Keep / Not this** remains the creative decision. A learned/hand-engineered metric that disagrees with those labels cannot gate promotion: freeze it as diagnostic-only, retain disagreement examples and revise/calibrate only on a separate set before reconsidering it. Familiar-character similarity, skeleton keypoints or aesthetic score alone cannot stand in for original-character retention or contact plausibility.

The incumbent choice is defeated if its bounded valid-completion set has fewer owner Keep decisions at equal attempt/intervention budget than the alternative, or if its runtime failures make the route operationally unacceptable. Newer model marketing, a successful loader, generic leaderboard preference, or a single attractive image cannot defeat or establish that choice.
